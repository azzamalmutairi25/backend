# اختبار الحمل — منصّة تمكين الكفاءات

أدوات قياس محلية بلا أي اعتماديات (Node وPHP فقط): مولّد حمل متعدّد النوى،
وموزّع أحمال، ومشغّل عنقود يحاكي شكل النشر على المخدّم.

```
load-test/
  loadtest.mjs   مولّد الحمل — سيناريوهات واقعية، مئينات، تقرير JSON
  balancer.mjs   موزّع round-robin + فحص صحّة + ملخّص توزيع
  cluster.mjs    يشغّل N نسخة من التطبيق خلف الموزّع ويوقفها بنظافة
```

---

## لماذا موزّع أصلاً؟

`php artisan serve` هو خادم PHP المدمج: **خيط واحد يُسلسل كل الطلبات**. الضغط
عليه يقيس الخادم التطويري لا التطبيق. فنشغّل عدّة نسخ خلف موزّع، فنقيس التوسّع
الأفقي — وهو شكل النشر المقصود على المخدّم (عدّة عمّال PHP-FPM خلف nginx).

`balancer.mjs` **أداة قياس لا بديل إنتاجي** عن nginx/HAProxy.

---

## التشغيل

```bash
# ١) تحضير مستخدمين ورموزاً وبيانات معزولة (قطاع LT وحده)
php artisan loadtest:prepare --readers=20 --writers=10 --candidates=300

# ٢) عنقود من ٤ نسخ خلف موزّع على 8080
node load-test/cluster.mjs --nodes=4 --port=8080

# ٣) القياس (طرفية أخرى)
node load-test/loadtest.mjs --url=http://localhost:8080 --vus=40 --duration=60 --mix=read

# ٤) التنظيف — يحذف القطاع والمرشحين والمستخدمين والرموز
php artisan loadtest:prepare --cleanup
```

### خيارات المولّد

| الخيار | الافتراضي | المعنى |
|---|---|---|
| `--url` | `http://localhost:8000` | الهدف |
| `--vus` | 50 | مستخدمون افتراضيون متزامنون |
| `--duration` | 60 | مدة القياس (ثوانٍ) |
| `--ramp` | 10 | تصعيد تدريجي — يمنع اندفاعة أولى تُشوّه p99 |
| `--mix` | `read` | `read` \| `write` \| `mixed` \| `public` |
| `--think` | 0 | زمن تفكير بين الطلبات (0 = ضغط أقصى) |
| `--workers` | الأنوية − 1 | خيوط توليد الحمل |
| `--out` | — | مسار تقرير JSON |

## لماذا الرموز تُصدَر بأمر لا بتسجيل دخول؟

حدّان يُفسدان القياس لو مررنا بهما:

- `/api/login` محدود بـ**١٠ محاولات/دقيقة لكل IP** — مولّد الحمل يستهلكها فوراً.
- كل مسارات `/api` محدودة بـ`API_RATE_LIMIT` (**٣٠٠/دقيقة لكل مستخدم مُصادَق**)
  أي **٥ طلبات/ثانية للمستخدم الواحد**. رمزٌ واحد يقيس المُقيِّد لا التطبيق.

لذلك يُصدر `loadtest:prepare` رموز Sanctum مباشرة لمجموعة مستخدمين — وهو أيضاً
أقرب للواقع: الحمل الحقيقي يأتي من مستخدمين كثيرين لا من واحد.

**السقف النظري = `API_RATE_LIMIT × عدد المستخدمين ÷ ٦٠` طلب/ثانية.**
٣٠ مستخدماً ⇒ ١٥٠ ط/ث. لقياس السعة الخام: ارفع `API_RATE_LIMIT` في `.env`
ثم `php artisan config:clear`.

> **429 ليست فشلاً.** التقرير يفصلها عن الأعطال عمداً — خلطُهما يجعل نظاماً
> سليماً يبدو منهاراً. الأعطال الحقيقية هي `5xx` وأخطاء الشبكة/المهلة.

## نتائج القياس المرجعية

بيئة: MacBook، ٨ أنوية، PHP 8.5.7، PostgreSQL محلي، `php artisan serve`،
مولّد الحمل على الجهاز نفسه. **أرقام نسبية لا سعة إنتاج** — المخدّم يختلف.

### التوسّع الأفقي يعمل

| التهيئة | ٨ مستخدمين | الإنتاجية | p50 | p95 | p99 |
|---|---|---|---|---|---|
| عقدة واحدة | بلا موزّع | **8.4 ط/ث** | 858ms | 1376ms | 2309ms |
| ٤ عقد + موزّع | خلف 8080 | **22.5 ط/ث** | 269ms | 830ms | 1233ms |

**٢.٧× إنتاجية و٣.٢× أسرع** بأربع عقد. لم تبلغ ٤× لأن قاعدة البيانات ومولّد
الحمل يتقاسمان الجهاز نفسه.

### نقطة الإشباع (قراءة)

٤٠ مستخدماً على ٤ عقد: **25.8 ط/ث**، p50 1445ms، p99 3989ms، **صفر أخطاء**.
الإنتاجية لم تزد عن ٨ مستخدمين (22.5) بينما تضاعف الزمن ٥ مرّات — أي أن
النظام **مُشبَع عند ~٢٦ ط/ث** بهذه التهيئة، والزيادة بعدها طوابير لا طاقة.

### مسار الكتابة — ⛔ عطل حرج

٨ مستخدمين، ترشيح كامل مع السيرة: **16.8 ط/ث محاولة، ٦٣.٩٪ فقط نجحت،
١٥٤ خطأ خادم (٣٦٪)**.

## ⛔ الاختناق الحاسم: توليد رمز المشارك

`Assessment::generateParticipantCode()` يقرأ ثم يكتب بلا قفل:

```php
$codes = self::where('participant_code', 'like', "$prefix-%")->pluck('participant_code');
foreach ($codes as $code) { $max = max($max, (int) $m[1]); }
return sprintf('%s-%03d', $prefix, $max + 1);
```

**سجلّ الأخطاء يؤكّد السبب:**

```
duplicate key value violates unique constraint "candidates_participant_code_unique"
Key (participant_code)=(LT-266)   ← ثلاثة طلبات متزامنة حسبت الرمز نفسه
Key (participant_code)=(LT-267)
```

عيبان منفصلان:

1. **سباق (correctness)** — قراءة الحدّ الأقصى ثم الإدراج بلا قفل ولا تسلسل
   قاعدة بيانات. تحت التزامن يحصل طلبان على الرقم نفسه فيسقط أحدهما بـ500.
   ظهر عند ٨ مستخدمين فقط؛ على المخدّم بعشرات العمّال سيكون أسوأ.
2. **كلفة O(n) لكل إدراج (performance)** — يجلب **كل** رموز القطاع إلى ذاكرة
   PHP ثم يحسب الحدّ الأقصى فيها. عند ١٠٠٠٠ مرشح في قطاع، كل ترشيح جديد
   يجلب ١٠٠٠٠ صفّاً. الكلفة تنمو مع نجاح النظام.

**العلاج المقترح** (لم أُطبّقه — تعديلٌ في مسار إنشاء المرشح يستحقّ قراراً مستقلاً):
تسلسل في قاعدة البيانات لكل قطاع (جدول `sector_counters` مع `UPDATE … RETURNING`،
أو `SEQUENCE` لكل بادئة)، فيصير الترقيم ذرّياً وبكلفة ثابتة. مع إعادة محاولة
واحدة عند 23505 كشبكة أمان.

## اختناقات أخرى مرصودة (ثابتة، من الإعدادات)

| البند | الحالي | الأثر تحت الحمل |
|---|---|---|
| `QUEUE_CONNECTION` | `sync` | جدولة الرسائل تُنفَّذ داخل دورة الطلب — كل ترشيح ينتظر بوّابة الرسائل |
| `CACHE_STORE` | `database` | كل قراءة/كتابة تخزين مؤقّت رحلةٌ إلى Postgres |
| `SESSION_DRIVER` | `database` | كتابة جلسة لكل طلب على القاعدة نفسها |
| Redis | غير مُشغَّل | البديل الطبيعي للثلاثة أعلاه |

هذه تطابق ما هو مخطَّط أصلاً: **الانتقال إلى Redis + Horizon قبل الإطلاق**.
بعد الانتقال أعِد القياس — الأرقام أعلاه هي خطّ الأساس للمقارنة.

## قراءة الأرقام

- **p50** تجربة المستخدم المعتاد · **p95/p99** تجربة أسوأ الحالات (هي التي تُشتكى).
- **إنتاجية ثابتة مع زمن متصاعد** = إشباع. زيادة المستخدمين بعدها تُطيل الطابور فقط.
- **5xx** أعطال حقيقية — راجع `storage/logs/laravel.log` فوراً.
- **مهلة/انقطاع** = الخادم بلغ سقف اتصالاته، أو المولّد أسرع من الهدف.
- **429** حدّ معدّل يعمل كما صُمّم.

## ملاحظات

- خليط `public` يضرب `/api/public/assessment/{token}/verify` المحدود بـ**٢٠/دقيقة
  لكل IP**، فسيمتلئ بـ429 من مصدر واحد. لقياسه فعلياً تلزم عدّة عناوين مصدر.
- سيناريو الكتابة يُنشئ مرشحين حقيقيين — كلهم في قطاع `LT` المعزول، ويزولون
  بـ`--cleanup`. لا تُشغّل خليط الكتابة على قاعدة إنتاج.
- `loadtest:prepare` يرفض العمل في بيئة الإنتاج إلا بـ`--force`.
- `tokens.json` يحمل رموز وصول صالحة — يُكتب بصلاحية `0600` ومُستثنى من git.
